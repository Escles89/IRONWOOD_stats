# Skill Mastery tracker

Issue: [#2](https://github.com/Escles89/IRONWOOD_stats/issues/2). The pending-loot extension remains separate in #3. During implementation the player replaced the persistent Status card with a modal opened by the mastery symbol, with a compact material list and completed masteries hidden from the selector. These changes supersede the original ticket’s panel placement and completed-selection presentation.

The feature lives in `apps/mastery/`. Runtime discovery uses the existing Angular router's Mastery component type and its named `MASTERY_DATA`, `MASTERY_COST`, `MASTERY_EXP` and `calcMasteryItems` bindings. Module/export identifiers are resolved from the current loaded client, without constructing components, hard-coding costs or calling gameplay endpoints. Unsupported or ambiguous bindings leave the feature visibly unavailable.

Mastery catalog item keys and values must agree with the native item ID; requirement calculation uses that item's native tier. Contributions come from `user.masteries.skills[id].items`, owned balances from `user.inventory`, and XP/coins from their separate native fields. Missing entries in an available inventory dictionary mean zero; absent dictionaries and malformed quantities remain unknown. Completed masteries may no longer retain contribution counts. A sparse `complete` flag on an existing progress record means incomplete, as on the native page; a missing progress record is unknown.

Selections and validated observations use `iw-status-mastery-v1:` scoped to the existing validated character/mode identity. They are independent of gameplay cache eviction. Changes are observed from the native runtime during normal rendering; they never open hidden routes or trigger daily work. Source ages advance only when the relevant quantities change or an explicit read confirms them.

Any observed contribution change invalidates the combined shortfall until a coherent native `getUser` synchronization succeeds. This conservative rule covers both material submission and Mastery Contracts without guessing their cause. It survives selection changes and reloads. Refresh shares the existing synchronization concurrency and identity checks; a failure retains observations and shows an error. Native synchronization confirms both balances, without starting/stopping actions, submitting items or claiming rewards.

## Validation evidence (2026-09-26)

- **Static native-client inspection:** verified the Mastery component bindings, per-item tier calculation, contribution map, sparse completion flags and material-submission inventory update. The code uses current native values, not the inspected numeric constants.
- **Harness workflows:** labelled selection, the 100/20/50 example, zero floors, contracts, submission reconciliation, selection/reload/mode/character isolation, incomplete data, read-only refresh, failure retention, completed-selection handling, modal open/close and absence of a persistent Status panel. Separate runtime-discovery coverage checks the native bindings without creating an Angular application.
- **Live read-only validation, Ironwood v1.6.5:** the local loader discovered all 17 masteries. Smelting matched the native page: Copper Bar required 15,000, contributed 24; Astral Bar required 105,000, contributed 5,629; Infernal Bar required 120,000, contributed 17,323. XP requirement was 24,000,000 and coin cost 10,000,000. Mining was already complete and omitted historical contribution counts. Under the final player amendment, completed masteries are omitted from the selector rather than shown with unknown historical quantities. Selection survived reload and no persistent tracker panel remains on Status or the native mastery page. Explicit read-only Refresh completed on Status with the current Chilli action continuing. The final compact Taming modal has eight resource icons and eight rows. At a 390 px viewport it fit without horizontal overflow and kept all four labelled quantities per row visible. The mastery, location and activity badges each measured 34×34 px. The final presentation uses the shared global dialog host with native select controls, a focus trap, Escape/Done/backdrop close and focus restoration. Keyboard selection changed Smelting to Smithing; Escape closed the final modal and returned focus to the mastery symbol.
- Live gameplay mutations were deliberately not exercised; submission/contract races are fixture evidence, not live mutation validation.
