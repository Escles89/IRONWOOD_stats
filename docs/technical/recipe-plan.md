# Recipe plans (#8)

Existing calculator records are retained without activation on load. An explicit Save & run plan writes the calculator target directly to the active recipe record and enables its automatic run. Edit seeds its draft from the active recipe; input edits are staged until Save and Cancel leaves the saved plan unchanged. Smaller chosen native batches and saved sources survive target edits. Satisfied targets stay saved and recalculate when their items are spent.

The recipe catalog adds the six gathering skills' current native action memberships to the existing crafting catalog. The shopping graph accepts this catalog, so shared gathering supplies, recipes and conversion inputs use the existing combined-demand stock allocation and cycle detection. Sole sources are saved at activation, including intermediate recipes; missing saved sources require another choice. Combat drops, purchases and conversions remain manual. Charcoal and Arcane Powder reserve recipe inputs before considering spare wood or gems; projected conversion output does not satisfy native readiness.

Steps are presented in dependency order. The first ready step is stable for unchanged observations; a selected ready alternative is preferred. The running action is excluded from starts, with pending loot shown separately from required acquisition. A following dependent action may be displayed as blocked. Partial observations remain unavailable, never zero. Observation changes recalculate without network reads. Explicit Refresh reads and validates the native user response without replaying action loops or daily work.

Native quantities describe Ironwood's primary-output limit, not attempts or guaranteed output. A supported single-unit primary drop provides a base or nominal suggestion. Unsupported output needs an explicit player quantity. For that start, known per-unit native costs and the native craft limit gate readiness, while total chain requirements remain unknown. Supported saved batches are capped to the latest remaining base or nominal suggestion, retaining smaller partial batches. Unknown yields retain explicit quantities; unique recipes still require exactly one. The effective quantity participates in the displayed start token, so an inventory change cannot silently dispatch a smaller replacement. Start revalidates the displayed token, owner, active record, current work, supplies, native controls and fresh server evidence. Changed steps reject the request; manual control requires another click and an automatic run stops for review. The existing guarded native start is reused; recipe starts require explicit idle and never authorize collection. Confirmed starts retain recipe plans. An enabled runner tracks the resulting batch before advancing later work.

Collection has its own Stop & collect / Collect completed work control and is also invoked by an enabled runner for due tracked work. It uses the mounted native page and an invocation-private guarded stop receiver. It checks the captured batch before stopping and again at the request, records the native collection receipt independently, and never calls Start. Collection errors or partial outcomes retain the plan. Manual start and collection pause the automatic run. Requirements are recalculated from the native observed inventory after collection, without carrying a stale pre-collection material refusal forward.

The combined editor opens over the current page. The shared Skills list on `/skills` and in the modal places the active skill beside a compact plan summary when space permits, stacking them in narrow containers, with the full Recipe planner panel below the remaining skills. Active plan, Calculator and Single action are separate views. Requirement rows disclose details on demand; the expanded row is keyed by owner, scope and item and survives observations. ## Automatic successive actions

`runner.js` implements automatic runs separately from the pure recipe calculation. Save & run plan enables a run; Pause and Resume are available in Active plan. Existing plans without a run record remain off. The action bar and idle header show a clickable planner icon with running, waiting, attention, paused and complete states.

The versioned `iw-status-recipe-run-v1:` record is scoped to character and game mode. It stores a run ID, exact saved-plan fingerprint, enabled state, status/reason, and tracked batch identity with its starting owned output balance. Target, source, conversion, quantity or next-step changes invalidate the old fingerprint. Saving enables the replacement plan; other edits require Resume. Completed targets end the run, so spending the target later cannot silently restart it. A matching current recipe action may be adopted on Save or Resume; unrelated work is left untouched until it ends and its loot is collected.

A two-second scheduler checks observed state only while the document is visible, script automation is enabled, and other shared work is idle. Draft edits hold progression. Web Locks provide a per-owner exclusive cross-tab lock for the complete transition. Browsers without Web Locks cannot enable automatic progression. Native requests use the existing Quick Skills shared busy guard. Every dispatch revalidates owner, run ID, plan fingerprint (including persisted cross-tab changes), visibility, automation permission, current batch, quantities and supplies. Pause during asynchronous preparation revokes a not-yet-dispatched request.

Finite work becomes due only when known native primary-output loot reaches its configured amount. Continuous gathering becomes due when known pending loot covers the recalculated remaining requirement. Estimated time is never completion evidence. Collection uses the existing guarded native control and checks that the exact tracked batch remains due immediately before dispatch. The runner requires a confirmed collection receipt and inventory progress, clears the tracked batch, and performs the next start on a later tick after a fresh inventory read. Native self-collection can also advance after a fresh read confirms an owned-output gain. It never treats pending loot or projected conversion output as owned inventory.

Starts reuse the existing guarded recipe start, including capped supported quantities and explicit quantities for uncertain yields. Late supply changes stop automatic preparation instead of opening a quantity prompt. Independent ready steps can proceed around manual requirements; if none is ready, the enabled run displays Needs attention and waits for observed inventory or requirement changes without repeating identical network reads. Purchases, combat-drop acquisition and inventory conversions remain manual.

Running batches survive reload and are reconciled against the observed action identity. A saved Starting or Collecting marker denotes an interrupted request with an unknown outcome and stops for review; it is never automatically replayed. Action replacement, failed requests, unconfirmed progress, or storage failures stop the run. Resume creates a new authorization and reconciles the current work. Confirmed collection remains independent of a later failed start.
