# Planned next action integration

Issues #6 and #7 add a Status-only card in `apps/planned-action/`. The catalog uses native skill membership, preserving both skill and action IDs and excluding Taming. Plans live separately from observations and Quick Skills history under `iw-status-planned-action-v1:` plus the existing serialized character/mode owner. Invalid records are rejected; missing catalog targets remain editable and cannot start.

The implementation calls the existing `quickResume` orchestration with a captured plan. It retains native route, quantity controls, request observation, confirmation and recap. Planned attempts finish with a read-only server check rather than replaying the native action service, which could retry collection; ordinary Quick Skills synchronization is unchanged. Planned quantities override Quick Skills amount preferences only for this attempt; shortage choices never write those preferences. An exact native start response clears the captured plan before later persistence, rendering or synchronization work.

## Completion and dispatch

The gate distinguishes explicit idle, completed finite work, unfinished finite work, continuous work and unknown state. Idle requires native `user.action === null`, explicit non-loading/non-syncing flags, and an empty known Current Loot map. Finite completion requires valid catalog membership, a positive native amount, a valid batch start date, and a known integer primary-output count in `action.actionLoot` at least equal to that amount. No estimate, missing markup, absent loop subscription or generic stop flag establishes completion. Continuous work requires a manual stop. A batch already collected by the game follows the explicit-idle path.

Preparation navigates the already-mounted native SkillPage with `skipLocationChange`, keeps Status visible and restores its previous source page afterward. It never bootstraps a fresh native app for this feature. Native `canStart$` and `uniqueCraftable$` remain authoritative. A completed batch targeting the same recipe opens the existing native amount dialog and submits its native Craft control.

The attempt captures the source batch's skill, action, start date, seed, amount and native options. After prompts, before native dispatch, at the native collection request and again at the target-start request, guards check character/mode, source batch, saved plan, catalog membership, known requirements, supply, quantity and contention. Fresh `getUser` reads verify the server still holds the expected batch, or explicit idle after this attempt's confirmed collection. The request does not apply the snapshot or replay native action loops: `handleActionSync` can automatically collect finished work and is inappropriate for a read-only gate.

The native target-start handler alone requests collection. The script never clicks a separate Stop & Loot control for a planned start. Its stop guard permits exactly one collection of the captured, still-complete batch. A synchronous guard also runs before the native collection handler can stop its local loop. The handler then sets its loading flag; only its own collection-request guard tolerates that flag. After a confirmed receipt, the shared native runtime must be explicitly idle, and non-inventory/non-coin requirements must still match the captured baseline. Inventory and coins can legitimately change during collection. A new batch, changed equipment, conflicting claim or timeout cancels continuation without retry. Per-invocation proxies give the native page handler and action service a private guarded Firebase receiver while forwarding ordinary state updates to the live services. Revoked guards stay captured by that invocation so a late collection response cannot start a target. The original live service methods are never replaced, so later manual activity is unaffected. Guard refusals use native observable errors, allowing native handlers to clear their loading flags; a refusal before entering the stop handler returns its ordinary false outcome.

Collection receipts and exact skill/action start responses are independent. Confirmed rewards remain visible after a rejected, wrong-target or unconfirmed start. Only a confirmed feature start clears the plan, even if native rendering or later synchronization fails. The native page must expose an eligible start control; native restrictions are not bypassed.

Explicit Refresh holds the existing coordination lock, reads current evidence, and inspects the target's native controls in the existing app. It records timestamped requirements, including failures, and never invokes daily work. Observation age alone never schedules a read. A source mismatch remains blocked until native state and fresh observations agree.

## Validation evidence

**Native-client static inspection:** `main.3ff34f86918fe4aa.js` (Ironwood v1.6.5) computes remaining finite output as `maxAmount - loot[firstDrop].amount`, floored at zero. SkillPage's `actionAmount$` reads that same primary-output count and renders it beside the configured amount. The native action service calls `handleStopAction` when simulation stops; this normally collects a completed batch automatically. A stopped loop or `history.stop` alone is insufficient: native work can also stop for depleted supplies. The target-start handler calls its own stop/collection workflow when an action remains, then requests the target start. Successful stop clears the action and its loot. These are static findings, not proof of live transition acceptance.
