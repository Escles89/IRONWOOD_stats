# Planned next action integration

Issue #6 adds a Status-only card in `apps/planned-action/`. The catalog uses native skill membership, preserving both skill and action IDs and excluding Taming. Plans live separately from observations and Quick Skills history under `iw-status-planned-action-v1:` plus the existing serialized character/mode owner. Invalid records are rejected; missing catalog targets remain editable and cannot start.

The implementation calls the existing `quickResume` orchestration with a captured plan. It retains the native route, quantity controls, request observation, confirmation, recap and synchronization machinery. Planned quantities override Quick Skills amount preferences only for this attempt; shortage choices never write those preferences. Exact target confirmation clears the captured plan before later persistence or synchronization work.

Idle requires native `user.action === null`, explicit non-loading/non-syncing flags, and an empty known Current Loot map. Undefined state, unavailable identity, route loading, retained loot and all non-null actions remain blocked. No timer or DOM absence establishes idle. Just before dispatch, the workflow checks ownership, captured plan, current catalog membership, idle, contention, relevant character requirements and quantity. It performs a fresh read-only synchronization and repeats those checks. A change between the main runtime and disposable target page refuses the attempt. At the native request boundary, it repeats the guard and verifies the exact amount. Planned starts revoke the frame's `stopAction` request, so even a native start handler encountering a new action cannot collect it to continue.

Refresh uses the same coordination lock and native read-only synchronization plus a disposable target page to inspect enabled/invalid controls. It stores a timestamped requirements observation. Known level and zero-supply blockers are also shown immediately from native effective-level and material-limit calculations; base XP alone never establishes ineligibility. It never clicks a start control or invokes daily work; observation age never schedules a frame. Native eligibility remains authoritative at Start.

## Validation evidence

Static inspection of the downloaded native client confirms that successful Stop & Loot sets `action: null` and clears the action loop, and that native target start calls its stop workflow whenever an action remains. Those findings justify the explicit-null idle gate and refusal of all stop requests in this slice. Finite completion is deliberately deferred to issue #7.

The assembled-userscript tests exercise rendered controls and delegated events with native runtime, storage, time and disposable-page fixtures. Coverage includes catalog selection, persistence/isolation, explicit idle, unknown/loading state, expired finite work, continuous work, shortages/cancellation, prompt-time changes, shared enemies, duplicate clicks, dispatch-time work, failure/timeout and synchronization failure after confirmed success. There is no TypeScript/typecheck configuration; repository checks validate JavaScript syntax, assembly and the test suite.

Live validation on 2026-09-27 observed active Fishing and, after the player changed activity, active Defense. Catalog filtering, native quantity labels, keyboard form submission, saved-plan reload, read-only native requirements refresh, disabled Start during active work, keyboard focus, and a 390 px mobile viewport without card overflow passed. The player’s chosen Imbuing → Regular Power Sigil plan was preserved. A live idle observation and deliberate idle-to-start transition have not been exercised; fixture and static evidence do not establish that live transition.
